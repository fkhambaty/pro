# Okavo — notes for an AI agent working in this repo

Okavo is a two-sided marketplace. Buyers describe software in plain language,
sign a scope ("the lock"), and identity-verified developers bid on that exact
scope. Live at <https://okavo.org>.

## Driving the app

There is a console for inspecting every screen and every row without clicking
through the interface:

```bash
node scripts/okavo.mjs help
```

| Command | What it does |
|---------|--------------|
| `check` | Confirm credentials are configured |
| `accounts` | Every user, role, verification state |
| `screens` | Every route and who may see it, read from the router |
| `token <email>` | A session token for any account, no password needed |
| `as <email> <METHOD> <path>` | Call the API **as that user**, row-level security applied |
| `db <table> [query]` | Read a table with the service role, **RLS bypassed** |
| `sql "<query>"` | Run SQL |
| `shot <path> [--as <email>]` | Screenshot a screen as that user |

The distinction between `as` and `db` matters more than anything else here.
`db` shows ground truth; `as` shows what one person is allowed to see. Most
access bugs in this codebase have been the gap between the two — for example,
a buyer's dashboard once listed other companies' requirements. When testing
permissions, always compare the two.

```bash
# Ground truth
node scripts/okavo.mjs sql "select count(*) from payments"

# What one buyer can actually read
node scripts/okavo.mjs as fk_qrf@yahoo.com GET "payments?select=id"
```

Set `OKAVO_SITE=http://127.0.0.1:5180` to drive the local dev server instead
of production.

## Credentials

`scripts/okavo.mjs` reads `.okavo-agent` in the repository root. That file is
gitignored and holds the Supabase service role key, so treat it like a
password: it can read and write every row in the database, including identity
documents and payments. Never paste its contents into a chat, a commit, or an
issue. If it is ever exposed, rotate the keys in the Supabase dashboard.

## Test accounts

and can be recreated at any time; the others are real.

## Ground rules

- **Never invent social proof.** No testimonials, customer logos, or usage
  numbers that are not real. The About page commits to this, and the homepage
  previously carried a fabricated "74 countries" claim that had to be removed.
- **Never claim a feature that is not switched on.** Escrow is built in the
  database but not enabled; the marketing copy says so explicitly. Keep it that
  way until it is true.
- Prices live in `apps/catalog/src/lib/pricing.ts`. Change them there, never
 inline, or the site will quote one number and charge another. Fees are shown
 in USD; Razorpay still collects INR equivalents until Stripe USD is live.
- Payment amounts are decided in the edge functions, never accepted from the
  browser, and a payment is only marked paid by a signature-verified webhook.

## Checking your work

```bash
cd apps/catalog && npx tsc -b --force   # `tsc --noEmit` alone does NOT check this project
npm run build                            # also prerenders the marketing pages
```

`npx tsc --noEmit` silently passes because the project uses TypeScript project
references. Use `tsc -b --force`.

## Layout

| Path | What |
|------|------|
| `apps/catalog/src` | The React app |
| `apps/catalog/api` | Vercel edge functions (analytics collector) |
| `supabase/functions` | Supabase edge functions (payments, signup alerts) |
| `supabase/migrations` | Schema, row-level security, views |
| `scripts` | Seeding, smoke tests, the agent console |
